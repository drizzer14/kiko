# iPad adaptive layout (ipad-phase3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Kiko runs natively on iPad with the Duo's device-agnostic layout rule plus three window-size rules (a 360 pt minimum pane, a 2/3 wide split at >= 1100 pt, a reflowing Statistics card grid), and the one-way device-family flip ships only in its own release after 1.3.

**Architecture:** Two branches. The track branch `ipad-phase3` (stacked on `duo-adaptive` 5a3dacaf) holds only device-agnostic code: the layout rule in `resolveLayoutMode`, a `companionShare` input to `resolvePaneGeometry` chosen per tab by a `wideSlot` in each stack's `PANE_CONFIG`, a screen-local `StatisticsGrid`, and the top-bar clearance. It is a no-op on every iPhone and Duo window, so it can merge without the flip. The branch `ipad-family` (own worktree, based on task 1/13's tip) holds the `TARGETED_DEVICE_FAMILY = "1,2"` flip, its pbxproj invariant and the 13-inch screenshots; it merges to main only when 1.3 has shipped or has its own release branch. Every simulator or device check runs on a SCRATCH build: a detached scratch worktree at the `ipad-phase3` tip with the flip commit cherry-picked on top, built by `kiko:ops`, never pushed, never merged, removed after the check. "The flip sha" is the task 2/13 step 5/6 commit (preflight R11).

**Tech Stack:** React Native 0.87.1, React 19.2.3, `@bottom-tabs/react-navigation` (react-native-bottom-tabs, SwiftUI TabView), `@react-navigation/native-stack`, `react-native-unistyles`, `react-native-safe-area-context`, `@react-native-documents/picker`, Jest 29 + RNTL 14, bash `scripts/checks/plist.sh`, Semgrep.

**Spec:** `docs/superpowers/specs/2026-10-17-ipad-adaptive-design.md` (builds on `docs/superpowers/specs/2026-10-08-iphone-duo-phase2-adaptive-design.md` and `docs/superpowers/plans/2026-10-08-iphone-duo-phase2.md`).

## Global Constraints

- Layout keys off the size class and the window or pane width only. No code reads the device idiom (`Platform.isPad`, `interfaceIdiom`, `userInterfaceIdiom`); task 4/13 adds a Semgrep ban.
- Grid columns by content width W (pane width, or window width in `single`): 1 when W < 700 pt; 2 when 700 <= W < 1000 pt; 3 when W >= 1000 pt.
- Wide split: mode `columns` and window width >= 1100 pt gives 2/3 to the tab's wide slot and 1/3 to the other; below 1100 pt equal halves. Home tab: companion 2/3. Statistics tab: primary 2/3. Accounts and Settings: halves. Rows are always halves. A fold overrides any ratio.
- Minimum pane 360 pt: `columns` needs window width >= 721 pt (2 x 360 + a 1 pt divider allowance); `rows` needs window height >= 721 pt; otherwise a regular window is `single`.
- Content cap `paneMaxWidth` 600 pt: in every pane, and in `single` on a regular window (centred). The Statistics grid at 2+ columns replaces it for the Statistics screen only. BottomSheet keeps `sheetMaxWidth` 540 pt.
- Resizes across 721 pt reuse the fold/unfold path and `SETTLE_DELAY_MS` 150 ms; crossing 1100 pt is geometry only (no mode change, no remount). Hysteresis only if task 9/13 shows a lost route.
- Every Duo pose unchanged (exact fixture values): outer 466x678 compact -> `single`; inner landscape 951x669 -> `columns`, equal halves (475 pt each with the fixtures' 1 pt hairline), 1 grid column; inner portrait 669x951 -> `rows`, equal halves (669 x 475), 1 grid column; half-open fold `{ x: 455.5, width: 40, height: 669 }` -> 455.5 pt panes; rows fold `{ y: 470, height: 24 }` -> 470 / 457 pt panes. Never `single` on the inner display.
- `sidebarAdaptable` stays off. Multiple scenes stay off. `Info.plist` keeps the scene manifest, all four `~ipad` orientations, the launch storyboard, and no `UIRequiresFullScreen`.
- Device family: `TARGETED_DEVICE_FAMILY = "1,2"` (quoted) in all three build configurations, ONLY on `ipad-family`; no 1.3 release branch or 1.3 archive may carry it (spec Section 1 item 6).
- Guideline 2.3.1(a): no `SCREENSHOT_MODE`, demo, seed, or flag in app `src/`; screenshots come from the manual procedure (`docs/harness/screenshots-check.md`) with the `e2e/screenshot/fixtures/` demo files through the real Import UI.
- No new dependency, no migration, no build/env flag. Code style per kiko-code-style (full words, fnts first, one unit per folder with `index.ts`, `@kiko/` alias, import length-sort).
- Each change set <= 30 mutable source files; count with `KIKO_MUTATION_BASE=<task base> make mutable`, never by hand.

## Review Focus

1. A Stage Manager resize across 721 pt with a detail open: the detail route survives in single and returns to its pane. Pinned in task 4/13 step 4/7.
2. A resize or rotation across 1100 pt with a detail open in the 2/3 slot: no remount, the same route keys, the mode stays `columns`. Pinned in task 5/13 step 5/8.
3. Every Duo pose unchanged (mode, equal halves, 1 grid column, never `single`). Pinned in task 4/13 step 1/7, task 5/13 step 1/8, task 6/13 step 1/8.
4. A filter, date-range change or a net-worth scrub on a 2-column grid: the grid does not re-lay-out and no chart remounts. Pinned in task 6/13 step 4/8.
5. The narrowest wide split (1100 pt): the 1/3 pane is >= 360 pt and a BottomSheet stays 540 pt centred in the window. Pinned in task 5/13 step 1/8; the sheet half by two labelled characterization pins in task 5/13 step 4/8 (the sheet passes `EQUAL_SHARE`, preflight R1).
